# Load test, 2026-08-13 — the hardened stack

First load test after the security-hardening run of 2026-08-12/13. Every
prior number in this project predates the NetworkPolicies, the Go 1.26 /
pgx 5.10 bump, the alpine 3.24 base, and scan-time ref validation, so the
question this answers is narrow and specific: **did any of that break or
slow the scan pipeline?**

Short answer: no. 95/95 scanned, zero failures, wall clock inside the
band of previous runs. The more useful output is the two runs that had
to be thrown away first, and why.

### What the 1330s does and does not say

It says the hardened stack completes the same workload cleanly. Nothing
regressed into failure: 0 scan errors, 0 evictions, and the
NetworkPolicies added in #55 blocked nothing they shouldn't — the
scan-worker egress rules carried 95 image pulls from eight public
registries, clamd traffic, and document uploads without a single denial.

It does **not** support "hardening cost ~10%". That reading compares one
run against one run. Known differences between this run and the 1210s
one, none of them controlled:

- 97 artifacts in the store rather than 94 (see "three new artifacts")
- disk began at 52% and peaked at 74%; the earlier runs' disk state was
  never recorded
- clamav autoscaled 2 → 10 during this run; prior scaling behaviour is
  not in the notes
- 51 scans hit the concurrency cap and retried (1272 retries total) —
  the earlier runs' retry counts were not captured

The honest summary is that 1330s sits between the two previous numbers
and that no single-run comparison can separate a real 10% from noise on
a shared laptop VM. **If a throughput regression ever matters here, the
harness needs to record retry counts and disk state per run, and each
configuration needs repeating.**

## The two runs that were discarded

Both failed for environmental reasons, and both are worth documenting
because they will happen again.

### Run 1 — image GC deleted the scan-worker image

Symptom: eight artifacts wedged in `scanning`, no progress for ten
minutes, `SCAN_CONCURRENCY=8` fully occupied.

Cause: every scan-worker Job pod on `k3d-...-server-0` was in
`ImagePullBackOff`:

```
Failed to pull image "monitor-api:dev": failed to resolve reference
"docker.io/library/monitor-api:dev": pull access denied, repository does
not exist or may require authorization
```

`monitor-api:dev` exists only because `k3d image import` put it in each
node's containerd. It has no registry to be pulled from. When the node
came under disk pressure, kubelet's image GC deleted it as an unused
image (`EvictionThresholdMet ... Attempting to reclaim
ephemeral-storage`), and `imagePullPolicy: IfNotPresent` then had
nowhere to fall back to.

**This is a standing hazard of the local-image workflow, not a one-off.**
It recurred later in the same session on `agent-1`. A Job that lands on a
node missing the image does not fail fast — it sits in `ImagePullBackOff`
holding a scan slot until the scan times out, so a single affected node
silently removes a quarter of the cluster's scan capacity.

Detection: `crictl images | grep monitor-api` on each node. Fix:
`k3d image import docker.io/library/monitor-api:dev -c <cluster>`.

### Run 2 — the API pod evicted itself out of the test

Symptom: 58/95 scanned, 29 `http-000` (no HTTP response) and 8
`poll-http-000`, and the client's port-forward dying with
`error: lost connection to pod`.

Cause: not a client problem. The node ran out of ephemeral storage and
kubelet evicted, among other things, **monitor-api itself**:

```
Warning Evicted pod/monitor-api-...   The node was low on resource: ephemeral-storage.
Warning Evicted pod/scm-docker-auth-... 
Warning Evicted pod/scm-clamav-...    (x3)
Warning Evicted pod/scm-scan-...
```

The `http-000`s were the client watching the server disappear. This
matches the earlier finding that HTTP 000 in this project is almost never
a network fault — it is something in-cluster failing and should be
diagnosed from cluster state, not from curl.

## The binding constraint is disk, not CPU

The podman VM backing this cluster has a 40 GiB disk. Every scan Job
extracts a full container image to `/tmp` (measured previously at up to
2.4 GiB), and the four k3d nodes each keep their **own** containerd image
store — the same images, duplicated four times.

| | |
| --- | --- |
| VM disk before cleanup | **95% (38G of 40G)** |
| after pruning build images | **68% (27G)** |
| node fs at run 3 start | 52% |
| node fs peak during run 3 | 74% |
| kubelet eviction threshold | ~85% |

Run 3 only succeeded because ~59 GB of accumulated build images were
pruned first. Both earlier runs began above the level at which a
95-image burst pushes the nodes past the eviction threshold.

**Before running this load test, check the VM has headroom.** Anything
above ~75% at rest will not survive `PARALLELISM=20`:

```bash
podman machine ssh 'df -h /var'          # want < 75%
docker image prune -f                     # reclaims build layers
k3d image import docker.io/library/monitor-api:dev -c supply-chain-monitor
```

## Three new artifacts

Registration in run 1 reported `3 created, 92 already registered`, where
the previous run reported `0 created, 95 matched by digest`. The corpus
did not change, so three upstream tags moved and their digests no longer
match the stored artifacts — the same mutable-tag drift previously seen
on `mongo:7` and `cgr.dev/chainguard/cosign:latest`.

That is the dedup logic behaving correctly (a moved tag genuinely is
different content), but it means the store now holds 97 artifacts for a
95-image corpus, and it will keep growing as tags move. Worth a periodic
prune rather than a fix.

## Final state

97 artifacts, all `scanned`; 45,305 findings; 0 scan errors; 0 pods
evicted during run 3; clamav autoscaled to 10 and back.

## Reproducing

```bash
make port-forward                        # separate terminal
SCM_API_KEY=$(kubectl get secret scm-monitor-api-auth \
  -n supply-chain-monitor -o jsonpath='{.data.API_KEY}' | base64 -d) \
  PARALLELISM=20 ./cluster/load-test-clamav.sh
```

Check first, in order: VM disk under 75%, `monitor-api:dev` present on
all four nodes, and no `Evicted` pods left over from a previous run.
